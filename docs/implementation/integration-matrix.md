# Phase 3 — Integration Matrix

How each module gets its data, and the cross-module links the spec requires.

## Data sources per module (Group 1)

| Module | Data source | Path |
|---|---|---|
| Sales Dashboard | Databricks `workspace.gold.*` | Angular -> `/api/sales/*` -> `SalesDashboardService` -> `DatabricksSqlClient` |
| Reports | Composed from other services (no direct Databricks calls except the Data Quality report) | Angular -> `/api/reports/*` -> `ReportService` -> `SalesDashboardService` / `CustomerAnalyticsService` / `AnalyticsService` / `PipelineRunService` / `DatabricksSqlClient`; persisted to Postgres `report_execution` |
| Customer Analytics | Databricks `workspace.gold.*` | Angular -> `/api/analytics/customers/*` -> `CustomerAnalyticsService` -> `DatabricksSqlClient` |
| Forecasting | Databricks `workspace.gold.salesorderheader` | Angular -> `/api/analytics/forecasting/*` -> `ForecastingService` -> `DatabricksSqlClient`; persisted to Postgres `forecast_run` |
| Anomaly Detection | Same as Executive Overview | Angular -> `/api/analytics/anomalies` -> `AnomalyDetectionController` -> `AnalyticsService#anomalies()` -> `DatabricksSqlClient`; ack/resolve persisted to Postgres `anomaly_acknowledgement` |

## Cross-module workflows implemented (Group 1)

1. **Sales Dashboard -> Customer Analytics**: clicking a Top Customers donut slice navigates to `/analytics/customers?search=<company>`, which pre-fills the search filter.
2. **Reports -> Sales Dashboard**: the Reports page's result panel has an "Open in Sales Dashboard" action.
3. **Executive Overview <-> Anomaly Detection**: identical `AnalyticsService#anomalies()` computation; the dedicated page adds filtering and persistent acknowledge/resolve on top, not a second detector.

## Group 2 additions

| Module | Data source | Path |
|---|---|---|
| Data Sources | Shared Databricks SQL Warehouse / this app's own Postgres pool | Angular -> `/api/sources/*` -> `DataSourceService` -> `DatabricksSqlClient` or `javax.sql.DataSource` |
| Data Pipelines | Databricks Jobs API | Angular -> `/api/pipelines/definitions/*` -> `PipelineDefinitionService` -> `PipelineRunService` -> `DatabricksJobsClient`; history in Postgres `pipeline_run` |
| Data Quality | Databricks `workspace.nexora.data_quality_report` | Angular -> `/api/data-quality/*` -> `DataQualityService` -> `DatabricksSqlClient` |

4. **Data Sources -> Data Pipelines**: a source's detail drawer shows `GET /api/sources/{id}/pipelines` (pipeline definitions referencing that `data_source_id`).
5. **Data Pipelines -> Pipeline Monitoring**: a pipeline's detail drawer links to `/observability/pipeline-monitoring` after triggering a run (built in Group 3, same `pipeline_run` records).
6. **Data Quality -> Data Pipelines**: "Execute checks" on the Data Quality page triggers the same pipeline definition Data Pipelines manages, then navigates to Pipeline Monitoring.

## Group 3 additions

| Module | Data source | Path |
|---|---|---|
| System Health | Real connectivity checks against Postgres, Databricks SQL Warehouse, Neo4j, Qdrant, Ollama, MinIO | Angular -> `/api/observability/system-health` -> `SystemHealthService` -> each dependency's existing client bean |
| Pipeline Monitoring | Same `pipeline_run`/`pipeline_definition` data as Data Pipelines | Angular -> `/api/observability/pipeline-monitoring/*` -> `PipelineMonitoringService` -> `PipelineDefinitionService`/`PipelineRunService` |
| Logs & Traces | This process's own Logback events + actuator httpexchanges | Angular -> `/api/observability/logs`, `/api/observability/traces` -> `LogsTracesController` -> `LogRingBuffer` / `HttpExchangeRepository` |
| Alerts | Derived from Pipelines, Data Quality, Anomaly Detection, System Health | Angular -> `/api/observability/alerts/*` -> `AlertController` -> `AlertRepository`; generated by scheduled `AlertEvaluationService` |
| Metrics | This app's Micrometer `MeterRegistry` (the same one Prometheus scrapes) | Angular -> `/api/observability/metrics/*` -> `MetricsController` -> `MeterRegistry` |

7. **Data Pipelines -> Pipeline Monitoring (direct link)**: triggering a run from Data Pipelines now navigates to Pipeline Monitoring (already linked in Group 2; confirmed here since Pipeline Monitoring exists as of this group).
8. **Data Quality -> Alerts**: `AlertEvaluationService` opens a WARNING alert whenever the latest data-quality run has failed checks, and auto-resolves it once a later run has none.
9. **Anomaly Detection -> Alerts**: the same high-confidence anomalies `AnalyticsService#anomalies()` and the Anomaly Detection page surface also open WARNING alerts (confidence >= 70), keyed by the same stable `key` used for acknowledge/resolve there.
10. **Pipeline Monitoring -> Alerts**: any pipeline run with a non-SUCCESS terminal result opens a CRITICAL alert.
11. **System Health -> Alerts**: any component reporting DOWN opens a CRITICAL alert.

## Group 4 additions

| Module | Data source | Path |
|---|---|---|
| AI Insights | Context Lake vector search + Knowledge Graph + local Ollama model | Angular -> `/api/ai-insights/*` -> `AiInsightsService` -> `DocumentSearchService` (Qdrant/Ollama embeddings) + `GraphQueryService` (Neo4j) + `OllamaChatClient` |

12. **AI Insights -> Context Lake**: every citation links to the source document (`openDocument` navigates to `/data-platform/context-lake`); the answer is never shown without the real chunks it was generated from.
13. **AI Insights -> Knowledge Graph**: each citation's "related entities" come from `GraphQueryService#traverse("document", id, 1)` — the same traversal Graph Explorer uses — following the real `(Document)-[:MENTIONS]->(Product|ProductCategory)` edges `GraphSyncService` already writes. Empty (not an error) if that document hasn't been graph-synced yet.
14. **AI Insights -> Context Lake (no sources)**: when nothing is indexed yet, the page's `NO_SOURCES` state links straight to Context Lake to upload a document, rather than a dead end.
